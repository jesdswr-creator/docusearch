## A. Integrity

### A1 — Verified good (no action)

- **`raw()` handle discipline holds.** The NOMUTEX main connection is touched from the UI thread only: `ensureBackfill()` phase queries run on the calling thread (all callers are UI-side: signals, timers, slots), the extraction continuation fires on the UI thread via `QFutureWatcher`, and embedding vector writes go through `BgeEmbeddingDb`'s *separate* connection opened with plain `sqlite3_open` (serialized mode). No cross-thread use of the main handle was found.
- **SQL injection surface: none.** Every query binds parameters; the only string-assembled SQL fragments are numeric literals (`LIMIT`, `SAVEPOINT sp_level_N` — integer-controlled). `LIKE` inputs pass through `likeEscape()`.
- **Teardown order is correct:** monitors stopped → extraction session invalidated (generation guard drops in-flight results) → search pool cancelled + joined → BGE init future joined → embedding pool drained → OCR pool shut down → FileWatcher stopped (quit + `wait(2000)`) → DB closed last.
- **GracefulDegradation ↔ OcrWorkerPool pause:** workers wait on a condition variable whose predicate includes `stopping_`, so shutdown during a pressure pause cannot deadlock.
- **Single-instance guard:** `QSharedMemory` attach/create; on Windows the kernel releases the segment on process death, so a crash cannot wedge the next launch.

### A2 — `BgeEmbeddingDb` missing `busy_timeout` (HIGH, one-line fix)

`BgeEmbeddingDb::open()` sets `journal_mode=WAL` + `synchronous=NORMAL` but no `busy_timeout`. The embedding tables (`BgeEmbeddings`, `EmbeddingChunks`) live in the **same database file** the main connection writes to continuously during extraction (per-file `DocumentText`/`SearchIndex` accounting on the UI thread) and during backfill phase 0 (stale-invalidation `DELETE` transaction in `ensureBackfill`). WAL permits one writer at a time; without a busy timeout, the embedding worker's `INSERT OR REPLACE` fails immediately with `SQLITE_BUSY` instead of waiting. `storeEmbedding()` returns false → the file counts as failed → **two consecutive busy-batches trip the deadlock guard and the whole AI backfill announces "AI indexing paused"** — a purely synthetic failure under real concurrent load.

**Fix:** `sqlite3_exec(m_db, "PRAGMA busy_timeout = 5000;", ...)` in `BgeEmbeddingDb::open()`.

### A3 — `OfficePreview` per-click connection lacks `busy_timeout` (LOW)

Fresh `SQLITE_OPEN_READONLY | NOMUTEX` connection per preview click, no busy timeout. In WAL modes readers never block, so impact is limited to non-WAL (LowEnd `TRUNCATE`) operation, where a concurrent writer's EXCLUSIVE phase makes the read fail → silent fallback to re-extraction. Same one-line fix.

### A4 — `Database::close()` rollback loop + ignored close rc (LOW)

`while (txnDepth_ > 0)` issues one `ROLLBACK;` per depth level; the first unwinds everything (savepoints included) and the rest are error no-ops against no active transaction. `sqlite3_close()`'s return code is ignored — a `SQLITE_BUSY` close (unfinalized statements) would leak the handle silently. Prefer a single rollback + `sqlite3_close_v2()` with rc logging.

### A5 — Savepoint naming: `ROLLBACK TO` never `RELEASE`s (LOW, cosmetic)

`rollback()` at depth > 1 executes `ROLLBACK TO SAVEPOINT sp_level_N` — which in SQLite leaves that savepoint open — then decrements `txnDepth_`. A later `begin()` re-creates the same name (savepoints are a stack of names, so this is consistent), and any commit/rollback at depth 0 discards the stack, so no leak is reachable in practice. Documenting the invariant would be enough; adding `RELEASE` after `ROLLBACK TO` would make the stack exact.

## B. Durability

### B1 — LowEnd tier: rollback journal + `synchronous=NORMAL` (HIGH, one-line fix)

`TierConfig` LowEnd: `journalMode = "TRUNCATE"`, and `Database::open()` unconditionally sets `synchronous = NORMAL` for local drives. Per SQLite documentation, `synchronous=NORMAL` is only safe from corruption **in WAL mode**; in rollback-journal modes (`DELETE`/`TRUNCATE`/`PERSIST`) a power loss at the wrong moment has a real (if small) chance of corrupting the database. The codebase's own network branch gets this right — it pairs `journal_mode=DELETE` with `synchronous=FULL` "safety first" — but the local LowEnd branch pairs `TRUNCATE` with `NORMAL`, which is strictly less safe than the network path it sits next to.

**Fix (either):** set `synchronous=FULL` whenever `journalMode != "WAL"`, or give LowEnd `journalMode = "WAL"` like the other tiers. The first is the conservative one-liner; the second also keeps LowEnd readers/writers concurrent.

Related note: pragma failures are only `DS_WARN`-ed — if `journal_mode=WAL` fails (e.g., transient lock), the DB silently runs in the default journal with `NORMAL`. Worth an `DS_ERROR` + fallback to `synchronous=FULL`.

### B2 — Backup/restore error paths (MEDIUM)

`SettingsDialog::onBackupNow` correctly runs `PRAGMA wal_checkpoint(TRUNCATE)` before zipping — good. Remaining holes in `BackupManager`:

- **Exit codes ignored.** `waitForFinished()` success ≠ compressor success; `restore()` returns `QFileInfo::exists(dbPath)` — which can be true for the *wrong* reasons or false after the old file is already gone.
- **Failed restore ⇒ blank database.** `restore()` does `QFile::remove(dbPath)` (rc ignored) *before* expanding. If `Expand-Archive` fails (e.g., the stats worker or embedding pool still holds the file open → sharing violation), the caller's reopen path runs `db_->open()` with `SQLITE_OPEN_CREATE` — creating a blank file — and does **not** call `Schema::initialize`. Result: "Restore failed." message over a table-less database; the app limps until restart, where schema init recovers an *empty* library. The index (not user files) is lost; a re-scan rebuilds it.
- **Torn-copy window.** Between `wal_checkpoint(TRUNCATE)` and PowerShell reading the file, worker-thread writers (stats scan, embedding batches) can commit — a live-file copy can catch a mid-write page. Low probability, but the correct tool is the SQLite Online Backup API (`sqlite3_backup_init`), which produces a consistent snapshot regardless.
- **Operational rough edges:** `Compress-Archive` with a 30 s timeout will fail on multi-GB databases (a 10 GB library compresses far slower); single-quoted PowerShell paths break on apostrophes (`O'Brien`); the manifest hardcodes `"version": "1.0.0"`.

**Recommended shape:** restore into a temp file first, verify `Schema::initialize` + a `PRAGMA integrity_check` on it, then atomically swap and clean `-wal`/`-shm`; report the compressor's exit code honestly. Reuse the `removeAndRebuildDatabase()` machinery for the reopen path.

### B3 — `enableBackupAutomatic` is dead config (MEDIUM)

Mid/HighEnd tiers declare `enableBackupAutomatic = true`, but nothing consumes the field — no automatic backup exists anywhere in the app. Either implement a simple post-scan checkpoint + scheduled backup, or remove the field so the tier story stays honest.

### B4 — Verified good (no action)

WAL auto-checkpoint at 500 pages; clean close removes `-wal`/`-shm` (which is what saves the normal restore path in practice); crash-restart relies on SQLite's WAL recovery, which is sound; the stats worker connection is `FULLMUTEX` + 5 s busy timeout (v1.7.11 fix); auto-scan has a 30-minute stuck watchdog; unavailable drives are skipped rather than pruned (no index wipe on a disconnected share); pragma failures are logged.

## C. Performance

### C1 — Verified good (no action)

- Semantic scan: rowid-range cursor (no `OFFSET` re-walk), 50 000-row cap, single scratch buffer, cooperative cancel checked every 4096 rows, LRU query-embedding cache; runs on its dedicated pool immune to extraction starvation.
- Keyword path: FTS5 `MATCH` parameterized, bm25 ordering, `LIMIT`-bounded, filename/FTS merge de-duplicated by id; hot filters (`status`, `hash`, `modified_date`, `extension`, `filename`) all have explicit indexes, and `Files.path` is `UNIQUE` (implicit index) — so the frequent `WHERE path = ?1` lookups (scan upserts, previews, purge) are indexed after all.
- `updateIndexStats()` is COUNT-aggregates only — not a folder walk; the full walk is confined to the hourly/auto scan with exclusion gates.

### C2 — 13 of 20 `TierConfig` fields are dead config (MEDIUM)

Actually consumed: `extractionWorkers` (global pool sizing), `ocrWorkers` (OCR pool size, clamped 1–4), `threadStackSize`, `databaseCacheSize`, `mmapSize`, `journalMode`, `busyTimeout`. **Never read anywhere:** `maxCachedResults`, `maxSearchChunkCache`, `maxTextPreviewCache`, `thumbnailCacheSize`, `ocrOutputCacheLimit`, `indexingBatchSize`, `indexingPauseMs`, `enableLiveIndexing`, `enableAutoScan`, `enableDuplicateDetection`, `enableImagePreview`, `enableOcrParallelism`, `enableBackupAutomatic`.

Consequence: the tier system tunes DB pragmas and worker counts, but a LowEnd machine still gets MidRange cache sizes, zero pause between indexing batches, live indexing on, image previews on, and duplicate detection on. This is the same "control that does not take effect" class as the v1.7.11 Settings pass. Either wire the fields to their obvious consumers (caches in the search/preview layers, `indexingPauseMs` → `ExtractionController::setTickIntervalMs` baseline, `enableAutoScan` → autoScanTimer gate, `enableLiveIndexing` → FileWatcher gate) or delete them from the struct so the tier table stops promising what it does not do.

### C3 — `statsDirty` fires per extracted file (LOW)

During a session, `statsDirty` is emitted per file (continuation), and each tick runs 3–5 COUNT queries on the UI thread plus label updates. Index-backed COUNTs on six-figure tables are cheap (≈1–5 ms), so this is acceptable today; at 500k+ rows, coalesce to a 1–2 s timer.

### C4 — `upsertFile` prepares per file (LOW)

The scan upsert prepares + finalizes two statements per file. Prepare cost (~10–50 µs ×2 × 100k files ≈ a few seconds per full scan) is dwarfed by disk I/O and hashing, but caching the two statements on the repository (or reusing the connection's prepared-statement cache) is an easy win.

### C5 — Three RAM pollers overlap (LOW)

`SystemHealthDashboard` (2 s), `MemoryMonitor` (5 s) and `GracefulDegradation` (10 s) each call `GlobalMemoryStatusEx` on the UI thread. Negligible CPU, but they could share one source-of-truth sample (MemoryMonitor already computes everything the other two need).

### C6 — `PRAGMA automatic_index = OFF` (note)

Intentional space choice presumably; current queries are covered by explicit indexes, so nothing regresses today. If future queries add un-indexed joins, this flag will silently force scans — keep it in mind.

## Recommended fix order

1. **B1** — LowEnd `synchronous=FULL` (or WAL) — one line, removes the only corruption-window class found.
2. **A2** — `BgeEmbeddingDb` busy_timeout — one line, removes a real spurious "AI indexing paused" trigger.
3. **B2** — restore-to-temp + validate + atomic swap; honest exit codes; `-wal`/`-shm` cleanup.
4. **C2/B3** — wire or delete the 13 dead TierConfig fields (and either implement or drop automatic backup).
5. **A3/A4/A5/C3/C4/C5** — polish batch.

Items 1–2 are two lines total; 3–4 are the substance of a v1.7.23 durability pass.
